Steve,

* What I set out to do

For fifteen letters I've been telling you, one theorem at a time, which
property of the error set a given law needed: commutativity here,
idempotence there. What I never did was put all of it in one place, or
check that what I'd told you actually matched what the proofs say. So
today I wrote a small Python script that reads every theorem in every
Lean file, looks at what each proof's text actually mentions, and builds
the table itself. If a theorem's proof doesn't say which property it
uses, the script refuses to guess: it stops and names the theorem. I
wanted a table that couldn't quietly drift away from the code, and a
list of everywhere it couldn't reach on its own.

The result is bigger than the fifteen letters: 146 theorems, not the
handful I'd been narrating. Two of my own earlier summaries turned out
to be wrong in the specifics. I'd said commutativity showed up in three
places; the mechanical count says six. I'd said the "at most one side
can fail" condition appeared in three places; it's four, and (this is
the part I got most wrong) it isn't the same finding four times.

* What the checker refused

The script's rule is deliberately unclever: scan a theorem's own
statement and proof for one of a dozen known property names
(=join_comm=, =join_idem=, and so on); if none appear, and the theorem
isn't on a short hand-checked list of "this one genuinely needs
nothing," stop. It found thirty theorems that named nothing. Most had a
boring explanation once I looked: a theorem like

#+transclude: [[orgit-file:~/src/steve-downey/lean-graded/integration/lean-model::blog/oracle-export::Graded/Widen.lean::42]] :lines 1-5 :src lean

never puts two error sets together at all: mapping a function and
widening the allowed errors are independent moves, so there's nothing
for any property to do. Reduction lemmas like "what does `ap` do when
both sides succeed" are the same story: the success case never touches
the union.

A more interesting group delegates. =canon_perm=, the theorem saying two
orderings of the same error kinds produce the same canonical form, does
all its work by citing another theorem (=joinAll_perm=) that already
carries commutativity and associativity honestly. The script can't
follow that citation, so it saw nothing, but the property is genuinely
recorded, just one theorem over.

The one I want to flag hardest is =flatten_ap=, the theorem explaining
exactly when collapsing two nested error-carrying values commutes with
combining them. Its proof cites no property at all, and unlike
=canon_perm= that's not because it delegates cleanly: it needs a grade
equation, proved by a separate helper (=Comp.grade_reassoc=) that uses
*both* associativity and commutativity, but =flatten_ap= reaches that
helper by name as a cast target, never by re-deriving the fact. A human
reading the proof can see the property is there; a script reading only
that one theorem's text cannot. I read every one of the thirty by hand,
decided each was either genuinely property-free or a clean citation of
an already-correct sibling, and recorded the reasoning next to the code
rather than silently widening what counts as "fine." None of them got a
free pass without a written reason.

* What changed

=scripts/laws-inventory.py= now exists, along with =docs/laws.md= and
=docs/laws.json= (the generated table), =docs/probe-harness.md= (one C++
equation per law that has one, for testing with real =std= types later),
and a =laws= target in the =Makefile= that regenerates and diffs the
table so it can't go stale. =docs/design.md='s laws-inventory section now
holds the corrected counts instead of my earlier guesses.

The corrected commutativity count taught me something I'd undercounted:
=Graded/Tuple.lean= uses it twice, not once: once in the theorem saying
order doesn't matter, and again in a helper that theorem's own
"duplicates collapse" cousin depends on. And the "at most one side can
fail" condition, which I'd been treating as one recurring idea, is
really four different answers to four different questions: load-bearing
in one theorem, present-but-not-needed in a second (a stronger,
unconditional proof existed all along), vacuously satisfied in a third
(the shape in question simply can't hold two errors), and a different,
three-part condition in a fourth. I'd flattened all of that into "the
same finding" before I had the table in front of me.

* Back in C++

This table is the appendix I owe the paper: for every law your compiler
would need to trust about a graded error type, here's the Lean theorem,
here's exactly which algebraic property of the error set it leans on,
and here's the C++ equation to go check against real =std::expected=
code. If you're building a *different* kind of grade than a set of error
types (counting instead of collecting, say) this table tells you
precisely which of your operations stay available at which layer: unit
and associativity alone gets you the monad and most of the applicative;
add commutativity and reordering guarantees hold; add idempotence (the
one =error_set= gets for free from being a set) and the traversal
signature that doesn't grow with input length becomes writable at all.
Whether idempotence is really a separate requirement or falls out for
free once you insist your grade is a genuine least upper bound is still
an open question on my end. I've flagged it rather than answered it,
because it changes how several rows in this table should be read, and I
didn't want to bake in an answer while it's still contested.
